# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is `github.com/evictedcucumber/packwiz`, a fork of [packwiz/packwiz](https://github.com/packwiz/packwiz), a CLI tool for creating Minecraft modpacks as version-controllable TOML metadata rather than raw JAR files. This fork only supports Modrinth as a mod source — CurseForge, GitHub releases, and direct-URL/local downloads have been removed from upstream. Packs created by this fork use a distinct `pack-format` (`evictedcucumber-packwiz:1.0.0`, see [core/pack.go](core/pack.go)) and are intentionally incompatible with upstream packwiz tooling.

## Commands

### Build

```bash
go build ./...
```

After any change, verify the project builds both ways CI and users build it:

```bash
go build ./...
nix build
```

`nix build` uses vendored dependencies pinned by `nix/vendor-hash`. If `go.mod`/`go.sum` changed, that hash must be refreshed: clear `nix/vendor-hash`, run `nix build`, and copy the `got:` hash from the failed build back into the file.

`nix build` only sees files git tracks, so a new, untracked file or package makes it fail (or silently build without it). Stage new files first (`git add -N` is enough), or build from a throwaway `git init` copy of the tree to leave the real index alone. `nix build` also runs `go test ./...` in a sandbox with no `git` binary.

If `go` isn't on `PATH` (this repo doesn't assume a global Go install), run it through the flake dev shell instead: `nix develop --command go build ./...`.

`go.mod`'s `go` directive is 1.26 because Bubble Tea v2 (the TUI) requires it; CI reads the version from `go.mod` (`go-version-file`), and the flake's nixpkgs provides it.

### Test

```bash
go test ./...
```

Run a single package or test (mirrors what CI runs, `-race -count=2`, for a specific package):

```bash
go test ./core/... -race -count=2
go test ./modrinth/... -run TestSomeName -v
```

### Vet

```bash
go vet ./...
```

### Nix dev shell

```bash
nix develop
```

Provides the Go toolchain plus `gopls`, matching `flake.nix`. `direnv` (`.envrc` has `use flake`) picks this up automatically.

## Architecture

Commands are registered into a shared root via a plugin-style `init()` pattern, not a single monolithic command tree:

- [cmd/root.go](cmd/root.go) defines the root cobra command and no flags of its own (a pack is always the `pack.toml` of the current directory, which the internal `pack-file` viper key defaults to and tests point elsewhere; colour comes from `PACKWIZ_COLOR` or the config file's `color`; the default completion command is disabled), and exposes `cmd.Add()` for other packages to register subcommands.
- [cmd/](cmd) holds source-agnostic commands: `init`, `list`, `refresh`. `update`, `pin`/`unpin` and `mark-dependency`/`unmark-dependency` (registered under `mr` by the `modrinth` package, as `packwiz mr update` and so on; their code stays here because it is source-agnostic). `update --all` counts the checks that failed and says "No updates found, but N files could not be checked" rather than "All files are up to date!" (its exit status is still 0 when some checks fail, as the TODOs there ask about); `update <name>` exits 1 when its check fails, as everything else that goes wrong in it does. `list` prints names, or with `--save`/`--output` writes them as a markdown file ([cmd/listmarkdown.go](cmd/listmarkdown.go)): `renderMarkdownList` is the pure part, taking `markdownEntry`s (a name and its metadata file's path relative to the pack) and putting them, sorted, under a heading for each kind, which `sectionOf` reads from the folders of the path (the first that is `mods`, `resourcepacks`, `shaderpacks` or `datapacks`, so a subfolder doesn't matter; any other folder is a section named after it, and a file in none is `Other`). Each entry is the name as a link to its Modrinth page (`modrinthPageURL`, from the `mod-id` in the update data, as `https://modrinth.com/project/<id>`, which Modrinth redirects to the right kind of project; no link for a file with no such ID) followed by ` — ` and its version (`core.Mod.DisplayVersion`, so the file name for metadata that records none), and there is nothing of `added-as-dependency`, so `--save` and `--output` (which implies `--save`) are cobra flag groups exclusive with `--version` and `--show-kind`, and `--side` and `--only` apply as they do to the plain list. Names come from Modrinth, so `escapeMarkdown` makes them show as written, and nothing that is written to the file is styled. The default file is `core.ModListFile` (`MODS.md`) in the pack's folder, which is in `ignoreDefaults` in [core/index.go](core/index.go) as `CHANGELOG.md` is, so `refresh` doesn't put it in the index and `git commit` and the changelog don't count it as config; a file that `--output` names inside the pack's folder isn't, and needs `.packwizignore`. `Run` still `os.Exit`s on an error, but `writeMarkdownList` returns it, so it is tested directly. What the TUI needs of the source-agnostic commands is here as functions that neither print nor prompt: `FindUpdates` and `ApplyUpdates` ([cmd/updates.go](cmd/updates.go)) are `update --all` without its output (`UpdateSearch` has the offers, the failures with how many mods each is for, the pinned and the unsupported, and `update --all` prints from it), `FilterByKind`/`FilterBySide`/`SortMods` are what `list` filters and orders with, `SaveModList` writes `MODS.md` as `list --save` does, and `CreatePack` (with `LoaderVersions` and `LoaderVersion`, which keeps the NeoForge 1.20.1 quirk in one place) is `init` without its questions, which `init` itself ends in too, so the two can't make different packs.
- [modrinth/](modrinth) implements the Modrinth source as a self-contained package: it registers its own `modrinth`/`mr` command (with `add [URL]`, `update`, `export`, `deps` subcommands) and the root-level `validate` and `fix` commands via `init()`, and implements `core.Updater` (registered into `core.Updaters["modrinth"]`) so the source-agnostic `update` can dispatch to it. [modrinth/api/](modrinth/api) is a thin REST client for the Modrinth API; the rest of [modrinth/](modrinth) contains install/export/dependency-resolution logic. `add` on a project the pack already has (found by its Modrinth project ID, since a metadata file can have any name) compares versions and, if they differ, asks before updating that mod in place rather than overwriting it: `applyVersion` in [modrinth/updater.go](modrinth/updater.go) is shared with `DoUpdate`, so the mod keeps its pin, option and so on, and a pinned mod is refused even with `-y`. Its latest version is looked up with the release type the mod was added with, so `add` and `packwiz mr update` agree on what is latest. `getLatestVersion` in [modrinth/modrinth.go](modrinth/modrinth.go) picks the newest by date, and warns when another version has a higher version number (`findHigherNumbered`). Only versions at least as stable are compared (so a beta running ahead of a release isn't a warning), and only those whose numbers are written the same way (`versionNumberShape`), because FlexVer gives nonsense for numbers in different formats: text sorts above a number, so it ranks `mc1.21.1-6.0.9` above `6.0.10+mc1.21.1`. A project that changed how it numbers its versions is therefore left unflagged rather than wrongly flagged. The loader tags authors put in their numbers are left out first (`comparableVersionNumber`), so versions that differ only by such a tag, like `neoforge_1.21-2.0.8` and `1.21-2.1.10`, still compare with each other. A NeoForge pack that has Sinytra Connector and Forgified Fabric API added (`runsFabricMods` in [modrinth/connector.go](modrinth/connector.go), which goes by their Modrinth project IDs) also accepts mods that only have a Fabric version: `getLatestVersion` looks for Fabric only when there is nothing for the pack's loader, so a NeoForge version always wins however old, and only a `noVersionsError` triggers it, so a failed lookup isn't taken for finding nothing. `add` says in a notice that such a mod runs through Connector, but `update` doesn't, as it would repeat it for every Fabric mod each time. Fabric API itself is never added: Forgified Fabric API stands in for it and the two can't be installed together, so it counts as already added when dependencies are resolved and in `deps`, and adding it directly is refused. `CheckUpdate` reads the index itself to know what the pack has, as the mods it is given can be just the one being updated. Modrinth lists some mods (world generation libraries such as Repurposed Structures) as unsupported on the client, which `getSide` makes `server`, but a mod on the client that requires one crashes without it, and so does singleplayer. So `promoteSides` ([modrinth/sides.go](modrinth/sides.go)) puts a `server` mod on both sides when a mod that runs on the client (anything not `server`) requires it, going by the `core.Mod.Dependencies` that metadata records (`widenSides` is the pure part, which follows a chain of requirements until nothing changes). `installVersion` runs it over the whole pack once the mod and its dependencies are added, so the order they were added in doesn't matter, and it saves what it changed and says so in a notice. Nothing else changes anything: a mod that gains a requirement in `update`, or metadata that predates recorded dependencies (`packwiz modrinth deps` fills those in), is only put right by the next `add`. `sidePromotions` is `widenSides` without the change (it works on copies), which `export` uses to warn and `validate` to report. It only widens `server` to `both`, never the other way, and there is no way to opt a mod out. `export` says what went into the pack once its files are downloaded: `breakdown` ([modrinth/breakdown.go](modrinth/breakdown.go)) is a table of each file's sides, size and path, in path order, with a summary line, and `exportEnv` is the one place that turns a side and `option` into the manifest's `client`/`server` values, so the table and the manifest can't disagree. Export prints nothing for each file as it downloads (nor does `cmdshared.AddToZip`), so the table is the one place each file is listed. `validate` ([modrinth/validate.go](modrinth/validate.go)) checks the pack without changing it: `validatePack` returns a `validation` (problems by metadata file, or by the pack under `""`) that `print` writes and the command's `Run` exits 1 on if it has any errors, warnings not failing it. It reads every metadata file the index lists on its own, so one that can't be read is an error and the rest are still checked; checks what each has (`checkMod`), duplicate projects and files, required and incompatible dependencies, side promotion, and `pack.toml`; and looks up on Modrinth, in batches, what a mod that records no dependencies depends on (which can't be told from one that has none), only reading them: what couldn't be looked up is one warning, not an error, so an offline run still finishes. Messages are stored plain and styled when printed. Its tests use `validatablePack`, which turns on httpmock with nothing registered, so a lookup a test didn't expect shows as a warning, and run the command again as a process for its exit status. `fix` ([modrinth/fix.go](modrinth/fix.go)) is `validate` followed by doing something about it: `runFix` validates and prints as the command does, `planFixes` works out the changes without making any (a `fixPlan` of changes by file: a file to create, a side, a version to record), `print` shows them, `cmdshared.PromptYesNo` asks, `apply` makes them, and the pack is validated again; the command fails if errors are left. It fixes a server-only mod that a client mod requires (`widenSides`, run on copies of the mods `validate` read); a required dependency the pack lacks (`findDependencies`, the loop `installVersion` runs to find them, and `newFileMeta`, which `createFileMeta` saves, so it is added as `mr add` would add it; the new mods join `widenSides` with the rest, so one Modrinth lists as server-only is added on both sides if a client mod needs it, and one that would replace a file that is already there is skipped, and said); a mod with no side (`both`, as it was treated); and a mod that doesn't record its version (`mrUpdater.ResolveVersions`). `apply` reads each file again and changes only what the plan says, so the dependencies `validate` looked up are never saved along with a side; each file is written once, and one that can't be changed doesn't stop the others. A mod made in memory has no parsed update data, so `projectIDOf` reads its project from what it would be saved with. `checkConfigFiles` checks who owns what: files that nothing claims, and entries that match no file, both for mods and, from `core.ConfigFileTree`'s `Owners`, for the pack and its loader in `pack.toml` (whose owner names are checked too, with `Pack.IsConfigOwner`); `fix` takes the entries that match no file out, and as those of the pack and its loader are in `pack.toml` and not a metadata file they are a `fixPlan.packChanges`, which `apply` writes with the pack, or on its own when no metadata file changed. Everything else `validate` finds needs a decision and is only reported. The commands print and ask as they go, which the TUI can't, so each has a quiet twin over the same code, in [modrinth/check.go](modrinth/check.go), [modrinth/add.go](modrinth/add.go) and [modrinth/exportpack.go](modrinth/exportpack.go), [modrinth/deps.go](modrinth/deps.go): `CheckPack` (a `Check` of `Finding`s by mod, and `PlanFixes` for the `Fixes` that `Apply` makes, on the pack as it is on disk then, not as it was planned); `PlanAdd` and `AddPlan.Apply` (`installVersion` is `newInstallPlan`, which asks nothing of Modrinth, `lookUpDependencies`, and `apply`, with `confirmUpdate` and the dependency prompt between them for the command, and `PlanAdd` runs the first two and reports, so what a person is asked comes at the same point either way; `Apply` reads the pack again and refuses if the project was added, removed or pinned since it was planned); `Search`, which is the only place a search is made (`Projects.Search` in [modrinth/api/](modrinth/api) with facets for the game versions and loader, and Fabric too when `runsFabricMods`); `Dependencies` (`scanDependencies`, `report`, and `Save`, which reads the pack again); and `Export` (`exportPack` is what `export` does from creating the zip on, returning an `ExportResult` whose `Breakdown` is the table, and removing a half written pack if it fails; the command passes `exportHooks` for the disclaimer and the manual-downloads list, which exits). They say what they would print through `internal/notice`, and each exported one collects it (`notice.Collect`) into a `Notices` field, plain. `getLatestVersion`'s warning, `noticeFabricMod`, `promoteSides`'s notice, `findDependencies`' errors and `cmdshared.AddToZip` all do, which prints exactly as before on the command line; a test that wants to know a function is quiet wraps it in `cmdtest.CaptureStdout` and checks for nothing.
- [utils/](utils) (`markdown`) is a self-registering command package, imported for side effects only (blank imports) from [main.go](main.go).
- [tui/](tui) is `packwiz tui`, the interactive interface, built on Bubble Tea v2 (`charm.land/bubbletea/v2`, with `bubbles/key` for bindings and `x/ansi` for measuring text; no lipgloss and no bubbles widgets, as a filter box and a border are a few lines and this keeps widths exact). It is a self-registering command package, blank-imported from [main.go](main.go), and like every command it changes a pack only through `core` and the commands' own code. It is every command on screens, in the order of `newScreens` ([tui/command.go](tui/command.go)), whose number is the key that goes to each (the help in `tuiCmd.Long` lists them by number, and a test keeps it in step): Overview, Mods, Add, Updates, Check, Deps, Config, Export and Release, and in a folder with no `pack.toml` only the init screen ([tui/initpack.go](tui/initpack.go), `packwiz init`), which has the app open the rest (`app.opened`, on `packCreatedMsg`) once it has made one. `app` ([tui/app.go](tui/app.go)) is a header, a row of the screens, one `screen` between them and a footer (`activate`, `update`, `view`, `setSize`, `keys`, `modal`, `working`); it owns `ctrl+c`, `q`, `?`, `tab`/`shift+tab` and the numbers, except that a screen that is `modal()` (a box or some text being typed) gets all of those itself, so they can be typed into a filter, and so a screen must not be `modal()` just because it was shown, or tab couldn't go through it (the add screen takes the keys after `/`, not on opening). `q` doesn't quit while a screen `working()` (a job that may be writing the pack), and `ctrl+c` always does. A screen learns its size from `setSize` (every screen, shown or not), never from being drawn, so its state doesn't depend on having been viewed, and `view()` returns exactly that many lines, none wider than the terminal: `TestEveryScreenDrawnFitsTheTerminal` ([tui/layout_all_test.go](tui/layout_all_test.go)) sweeps every state of every screen over terminal sizes, with colour and without, on a pack with names too long for any of them, and has found real bugs (text with a line break in it); add a state there for every screen state that draws something new. Every message that isn't a key is given to every screen, as what a job comes back with is for the screen that started it, which may not be the one shown: so each screen's messages have a type of their own, and a job's carry its number (below). Work off the update loop is a `tea.Cmd` that captures only the backend and returns a message, so the model is only touched by `Update`: a `worker` ([tui/task.go](tui/task.go)) starts a job (`start(text, work)`, with `progress(text)` for what to say while it runs) and takes the messages that are for its job number (`receive`), a `page` ([tui/page.go](tui/page.go), embedded by every screen after config) has the size, the status line, the worker and the box that is open, and lays a screen out as a summary line, a body and a status line (`render`). Reading the pack when a screen is shown is `exclusive`, not a job, so it doesn't stop keys. `backendLock` lets one job or read on the pack run at a time, whichever screens they are for, because `core` keeps its settings in viper, which isn't safe to touch from two goroutines, and notices are collected in one place; a screen that has to wait says what it is doing meanwhile. Jobs that change the pack re-read what they change from disk (`applyUpdates` re-reads each mod and won't update one that has been pinned since; `Fixes.Apply`, `AddPlan.Apply` and `DependencyReport.Save` read the pack again), so what was planned a while ago is never written over what was changed since. Other parts: `scroller` (cursor and offset in a list), `report` ([tui/report.go](tui/report.go): text that is read, made for a width, so it wraps, and scrolled), `searchBox` ([tui/search.go](tui/search.go): a `/` search, which the mods screen uses), `wrap` (hanging indent, knows about styling and line breaks) and `confirmBox`/`promptBox` ([tui/dialogs.go](tui/dialogs.go): `overlay`s that take every key while they are open, for yes/no with a list that scrolls, for just reading, and for a line of text). Each screen works on the pack through an interface of its own (`modsBackend`, `updatesBackend`, `addBackend`, `checkBackend`, `depsBackend`, `exportBackend`, `releaseBackend`, `overviewBackend`, `initBackend` and, for config, `configBackend` in [tui/backend.go](tui/backend.go)), in the `backend_*.go` files, all of which `packBackend` implements by reading the pack again on each call and using the quiet functions above, so that what it writes is what the commands write, and so a test can give a screen a fake (`fakeAdd`, `fakeExport`, `fakeRelease`, `fakeInit`, `fakeBackend`) for what needs the network or hides an error. The Updates, Check, Deps and Release screens are not run on opening except for the ones that are cheap and mostly local (Check, Deps and Release do the first time, once; Updates and the rest wait to be asked): each is a job and says so. The add screen searches Modrinth (`modrinth.Search`, which the commands have no twin of) and takes a URL, slug or ID as well; `enter` searches, or plans the result under the cursor if the query is what was searched for, or plans the URL typed. The config screen ([tui/config.go](tui/config.go)) is `packwiz config list` and `config relate` on one screen, plus taking a claim out again. Who can own a file is an `owner` ([tui/owner.go](tui/owner.go)): a mod, the pack as a whole or its loader, which the tree's groups, the rows and the picker all treat alike (`owner.key` is what tells them apart), so only `packBackend.relate` and `unrelate` know where each is written: a mod's file through `Index.SaveMod` and `Pack.SaveIndex`, the pack's and the loader's in `pack.toml` through `Pack.Write` alone, unless a mod was changed too, when `SaveIndex` writes the pack with the claims already applied to it. The picker lists the pack and the loader first, as `config list` does, then the mods. `buildRows` ([tui/configrows.go](tui/configrows.go)) is its pure part (the `core.ConfigFileTree`, the state filter and the folded groups become rows); relating opens a `picker` and unrelating an `unrelatePrompt` ([tui/overlay.go](tui/overlay.go)). Relating acts on the marked files, else the row under the cursor (a group being all of its files), and a file can be claimed as itself or as its folder (`picker.files`/`folders`, written by `core.ConfigEntry`, so a pack with a config folder gets entries without it, and `core.ClaimingEntries` finds what has to be removed to unclaim a file). The config screen's own work is `changedMsg`/`refreshedMsg`/`loadedMsg` and `busy`, from before `worker` existed; while it is busy keys that would change the pack are ignored, and the pack is read again after every change, even a failed one, as it may have been made in part. The TUI's searches are all fuzzy, with [internal/fuzzy/](internal/fuzzy) (below): the picker's filter over each owner's name and then its slug (`matchOwner`; `refilter` ranks by score and then the shorter name, as fzf does, so `enter` takes the best match), `/` in the config tree, which `buildRows` applies as a `fuzzy.Query` (`searchRows`): a file's row stays if every word is in its path or else the name of its group, so its group is there if any file is, and `count` and `files` are what matched, which is what marking or relating a group acts on; and `/` in the mods screen, over the name and then the slug. A search ignores folding, as a match would be hidden in a folded group, and the tree comes back folded when it is gone. While it is typed the screen is `modal()` (so `q` and `?` are letters of it) and the prompt is the status line; `rebuildForSearch` puts the cursor on the best-scoring file (the first of equals) only when the search changes, where `rebuild` keeps it on its row; `esc` clears a search that is left on before it unmarks. `highlight` picks out the matched runes (positions are indexes of runes, not bytes). The cursor is kept on its row across a rebuild, and follows a file to the group it moves to (`locate`). **Nothing may write to stdout while the TUI runs**, as it would be drawn over the screen, **and nothing may read stdin**, which the program owns: that is why `Index.RefreshQuietly` exists, which has no progress bar and returns the notice that files left the index (see `keepConfigDirFiles`) as plain text for the status line, where `Refresh` prints it, why prompts (`cmdshared.PromptYesNo`) are questions a screen asks before it calls the function that does the work, and why the TUI calls only the quiet functions, each of which has a test that wraps it in `cmdtest.CaptureStdout` and expects nothing. Colour is the roles of [internal/ui/](internal/ui) only, never colours of the TUI's own, so `PACKWIZ_COLOR` and `NO_COLOR` apply, and what is selected or marked has a symbol as well as a style, as colour only adds.
- [changelog/](changelog) manages a pack's release history (`packwiz changelog`, `packwiz changelog release`), and makes it from the git log. `RunRelease` first has the repository commit everything pending (`Repository.CommitPending`, which is `packwiz git commit` except that it errors, committing nothing, if the pack's folder has changed files packwiz doesn't recognise), then reads the commits made since the last release's recorded `Release.Commit` (`Repository.Log`; `--since` overrides it, and a history from before commits were recorded falls back to the last commit that changed `changelog.toml`), and `ChangesFromCommits` ([changelog/commits.go](changelog/commits.go)) reads them as conventional commits. What `packwiz git commit` writes is read back exactly (the regexes in `commits.go` and `line()` in [git/message.go](git/message.go) are the two ends of that format, kept in step by a round-trip test in the git package), several commits to one mod or file are squashed to their net effect, and any other `feat`/`fix`/breaking commit becomes a `Note` that counts towards the bump in its own words. The versioning policy lives in `Change.Bump()` in [changelog/diff.go](changelog/diff.go): any change to a server or both-side mod is major, adding/removing a client-only mod is minor, client-only mod updates and config changes are patch, and a note is bumped by its own type. The first release has no log to read, so it describes the pack as it is (a `Snapshot` diffed against nothing). `git` imports `changelog`, so `changelog` can't import it back: it defines `Repository` and `OpenRepository`, and [git/changelog.go](git/changelog.go) implements and registers it in `init()`, the same way `core.Updaters` is filled. A pack that isn't in a repository still gets a changelog: `OpenRepository` fails with an error that is `changelog.ErrNoRepository` (made by `changelog.NoRepository(reason)`, which `openRepo` in [git/repo.go](git/repo.go) uses when git isn't installed or the directory isn't in a working tree, so `packwiz git` reports it as its own error), and `openRepository` in [changelog/command.go](changelog/command.go) turns that into a nil `Repository` and a notice. `loadPending` then has no log to read: the first release is unchanged and later ones are `Diff`ed against `History.Snapshot`, which a release made without a repository keeps and one made with a repository clears (the log takes over, so an old snapshot mustn't linger to be compared with). Nothing commits without a repository, so `RunRelease` skips `CommitPending` and `pending.save` writes what committing would (`Index.RecordVersions` and the refreshed index, before `pack.toml`'s index hash is updated). `--since`, and a last release that was made from the log (so kept no snapshot), are errors, which `checkWithoutRepository` finds before the pack is loaded as loading it can need the network. Any other failure to open the repository is still an error, not a missing one. A pack put in a repository after releases made without one is released from the log from then on (from `LastChangedIn(changelog.toml)`, as for a history from before commits were recorded), so what changed between its last release and the first commit isn't listed. `CHANGELOG.md` is rendered from `changelog.toml` (`RenderRelease`, plain), and the preview that `packwiz changelog` prints goes through the same code with `style{colour: true}` (`renderRelease`), which colours pieces as they are built rather than reading Markdown back, so the text can't differ between the file and the terminal. `CHANGELOG.md` and `changelog.toml` are in `ignoreDefaults` in [core/index.go](core/index.go) so they aren't shipped inside the pack. A mod's version is what it records (`core.Mod.Version`, written by `add`/`update`); for mods that predate the field, `changelog.LoadWorking` asks their updater (`core.VersionResolver`, implemented by the Modrinth updater) and keeps the answer in memory, and only the writing path (`packwiz git commit`, which `RunRelease` runs) saves it with `Index.RecordVersions`, so previewing never touches the pack. A snapshot records a mod's file name when its version is unknown, so `modUpdated` in [changelog/diff.go](changelog/diff.go) treats a version that has merely become known for the same file as no change (which would otherwise make a server mod's commit look like a major update), and `History.UpgradeVersions` replaces file names in past releases where the mod is still on that file. `RunRelease` and `runPreview` are the command: what the TUI calls are `LoadPreview` (a `Preview`: the release, whether the pack is in a repository and why not, what the last release was, and `Text()`, the text `packwiz changelog` prints, which a test keeps equal to the command's), `MakeRelease` (releases without asking or printing, and returns the commits it made first, which it asks for from a `Repository` that implements the optional `CommitReporter` instead of having `CommitPending` print them) and `SaveMarkdown` (`changelog --save`, which lists the changes not released yet above the releases, from `unreleasedChanges`, and returns what it said as notices). `RunRelease` and `MakeRelease` are both `makeRelease` with different `releaseHooks` (show, confirm, committed, nothing), so they can't release differently. Whether the index refresh shows a progress bar is decided by `notice.Collecting()` (`refreshIndex`), so code that may run on either side needn't be told which.
- [git/](git) implements `packwiz git commit` and `packwiz git release` by shelling out to the `git` binary (no Go git dependency). It describes changes by diffing `changelog.TakeSnapshotFrom` a `HEAD` read straight out of git (`core.ParseIndex`/`core.ParsePack`/`core.DecodeMod` parse the committed bytes) against the working tree, so it reuses `changelog.Diff` and the bump policy rather than classifying anything itself. It also supplies the log to the changelog: `gitRepository` in [git/changelog.go](git/changelog.go) implements `changelog.Repository` (`git log --reverse --no-merges` for `Log`, and `pendingCommits` from the same plan `commit --dry-run` prints). Both commands need a repository, so `prepareCommit` and `runRelease` open it before anything else (loading the pack looks up versions over the network) and refuse outside one, with nothing printed or written. `commit` makes one commit per added/updated/removed mod, then one per added/changed/removed config file, then one `chore(pack)` commit for what else changed among the files packwiz recognises, such as a pin ([git/commit.go](git/commit.go)); it only ever commits paths it recognises (`committer.known`: what the index lists now and at `HEAD`, the index, `pack.toml`, `changelog.toml`, `CHANGELOG.md` and `MODS.md`) with `commitPaths`, never `git add -A`, so anything else that changed (`committer.unknown`, from `dirtyFiles`) is left uncommitted and listed by `warnUnknown`, and `gitRepository.CommitPending`/`CommitPendingReporting`, which a release commits with, fail with `errUnknown` before committing anything (`commit` and `commit --dry-run` don't), and `commitRelease` commits only `changelog.toml`, `CHANGELOG.md` and `pack.toml`; each commit is a consistent pack, so before each one `committer.writeIndexAndPack` writes an index (`HEAD`'s with only the mods committed so far applied) and a `pack.toml` (`HEAD`'s with just that index's hash), and the working tree is put back to the final index and `pack.toml` afterwards, including when a commit fails. The commit-type-to-bump mapping (`feat!`/`feat`/`fix`) is documented in [git/message.go](git/message.go). The TUI uses `PlanCommit` (the messages `commit --dry-run` would print), `CommitAll` (`committer.run` with a `report` function for the commits, which the command makes print) and `ReleaseAndTag` (`changelog.MakeRelease`, then `commitRelease`, which `runRelease` also ends in), none of which print.
- [core/](core) has no dependency on `cmd` and holds the domain model shared by everything above: `Pack` ([core/pack.go](core/pack.go), the `pack.toml`), `Index`/`IndexFiles` ([core/index.go](core/index.go), [core/indexfiles.go](core/indexfiles.go), the `index.toml` manifest of tracked files), and `Mod` ([core/mod.go](core/mod.go), one TOML file per installed mod). [core/interfaces.go](core/interfaces.go) defines the `Updater` and `MetaDownloader` extension points that source packages implement, plus the optional `VersionResolver` an `Updater` can also implement. The pure helpers for `config-files` entries live in [core/configfiles.go](core/configfiles.go) and are shared by `config relate` and the TUI: `ConfigEntry` (a path in the index becomes an entry, with the config folder taken out), `EntryClaims` and `ClaimingEntries` (which entries claim a file, with the config folder put back). `Index.SaveMod` writes a mod's metadata file and records its hash, and `Pack.SaveIndex` writes the index, the hash the pack records for it, and the pack, which is what has to follow a change to the index. Config files belong to a mod, to the pack's mod loader or to the pack as a whole, so what isn't a mod's is in `Pack.ConfigFiles` (`pack.toml`'s `[config-files]`, keyed `core.ConfigOwnerPack` or the loader's name as in `[versions]`, in the same entry format as a mod's; nothing derives it, `options.txt` is the pack's once it is related), with `Pack.ClaimConfigFile`/`UnclaimConfigFile` mirroring `Mod`'s except that an owner left with no entries is dropped, where a mod's empty list stays as a field to fill in. `Index.ConfigFileTree(mods, pack)` returns `Owners` (the pack, then its loaders; an owner the pack doesn't have is still shown, as written, so its files don't look unclaimed, and `validate` reports it) beside `Mods` and `Unclaimed`, with `resolveClaims` the one place that turns entries into the files they claim and the ones that match none. Only the index is hashed, and `pack.toml` isn't in it, so changing what the pack or its loader claims is a `Pack.Write` on its own, where changing a mod is `SaveMod` and then `SaveIndex`.
- A pack with a mod that reads the pack's files from a folder of its own (Configured Defaults, `configureddefaults/`) tracks only that folder and its metadata files. `core.ConfigDirResolver` ([core/configdir.go](core/configdir.go)) is the optional interface an `Updater` implements to say so, as `core.VersionResolver` is for versions, and the Modrinth updater does, going by Configured Defaults' project ID (`configuredDefaultsProjectID` in [modrinth/configureddefaults.go](modrinth/configureddefaults.go)). `Index.Refresh` asks it (`keepConfigDirFiles`, of the metadata files it finds on disk rather than the ones in the index, so a mod added by hand counts) and drops every other file that isn't a metadata file, saying how many of them the index had. Nothing else needs to know: export, `git commit` and the changelog all read the index, so what they call config follows the folder. `.packwizignore` can't override it, and `Refresh` now fails on a metadata file it can't read, as it has to read them. `cmdtest.RegisterConfigDirSource` is the stub source for tests outside `modrinth`.
- [internal/fuzzy/](internal/fuzzy) matches text the way fzf does, with fzf's own algorithm (`github.com/junegunn/fzf/src/algo`, `FuzzyMatchV2`) used as a library rather than by running the `fzf` binary, so nothing has to be installed, no process starts per key, and the nix sandbox and Windows need nothing. It is a leaf package, so the TUI and `core` both use it. A `Query` is whitespace-separated words that must all match, in any order, without regard to case or accents; `Query.Match(texts...)` finds each word in the first of several texts that has it (a name, then a slug; a path, then a group's name) and returns the score and, for each text, which characters matched (as indexes of runes, for showing them). `src/algo` isn't a supported API of fzf, so its version is pinned in `go.mod` and upgrading it means re-running the tests, which pin the ranking. The same matcher is used for a mod given on the command line: `Index.SearchMods` ([core/index.go](core/index.go)) ranks the mods by name and slug (ties: the shorter name, then the file, so the order never depends on the index being a map), and `resolveMod`/`findMod` ([cmd/modref.go](cmd/modref.go)) are what `pin`, `unpin`, `mark-dependency`, `unmark-dependency`, `update <name>` and `config relate --mod` look a mod up with: an exact slug, file name or path (`Index.FindMod`) is always the mod, and only when there is none is what was given searched for, taking the one mod that matches (and saying so) but never choosing among several (they are listed) and never searching for something with a folder in it, so nothing that worked before works differently. Errors are plain, as they never carry styling; `findMod` prints them. 
- [internal/notice/](internal/notice) is what code that does the work of a command says as it goes (a version was chosen although another has a higher number, a mod runs through Connector, a download failed and the rest carried on), so that the work can be used by the command line and by the TUI unchanged. `notice.Warnf(...)` and the rest print a styled line, exactly as `ui.Warning.Printf` did, unless `notice.Collect(fn)` is running `fn`, which returns what was said instead, in plain text, for the caller to show where it likes (`Collecting()` says so, for work that would otherwise draw a progress bar). Collecting is process-wide and not reentrant, so the TUI's `backendLock` is what keeps two collections from overlapping; don't call `Collect` from work that `Collect` is running. Only what is said along the way goes through it: a command's own output, what it is for, is printed by the command, and the quiet function returns that instead.
- [internal/ui/](internal/ui) colours command output, and is a leaf package (it imports nothing of packwiz's) so every package can use it. Styles are named for their role, not their colour, so how they look is decided in one place: `ui.Error`, `ui.Warning`, `ui.Success`, `ui.Info`, `ui.Muted` and `ui.Bold`, each with `Sprint`/`Sprintf`/`Printf`/`Println` that work like `fmt`'s (`Printf`/`Println` write to stdout, where every command prints). **Colour only ever adds to text**: with it off each returns its text unchanged, and with it on `ui.Strip` gives that same text back. So a message is worded the same either way, and new output should be written by putting the whole line in the style of what it says (`ui.Error.Println(err)`, `ui.Success.Printf(...)`) with `ui.Bold.Sprint(name)`-style emphasis inside, never by adding a prefix or symbol. Styles nest (a style inside another ends with a reset, which the outer one starts again after) and each line is styled on its own, ending before its line break. Only style at the point of printing: never put a styled string in an `error`, a file, a git commit message or `CHANGELOG.md`. Whether to colour is decided each time, for the stream the text is going to: `os.Stdout` (`term.IsTerminal`, so a test that captures stdout through a pipe gets plain text with no setup) unless the style is `.For(f)` another file, such as `ui.Error.For(os.Stderr)`, which `Printf`/`Println` then write to. Each stream is a terminal or not on its own (`ui.EnabledFor(f)`). It is decided by `PACKWIZ_COLOR=auto|always|never` or `color` in the config file, applied by `applyColor` in [cmd/root.go](cmd/root.go): `always` wins over everything, and `auto` is off for `NO_COLOR` and `TERM=dumb`. Windows consoles need virtual terminal processing turned on first, and the terminals of Cygwin, MSYS2 and Git Bash (mintty) aren't consoles but pipes to a pseudo-terminal, told apart only by the name of the pipe: `isCygwinPipeName` ([internal/ui/cygwin.go](internal/ui/cygwin.go)) is tested everywhere, but the calls that read a name and turn on the console are in [internal/ui/terminal_windows.go](internal/ui/terminal_windows.go), which has only been compiled (`GOOS=windows go vet ./...`), not run. `ui.Prompt` styles a prompt from its shape (the question in bold, `[default]` in cyan, `(choices)` faded), which is why `cmdshared.PromptYesNo` and `initReadValue` style their prompts themselves and callers pass them plain. `ui.Transition(from, to)` shows an update as red old, green new. Help and usage are coloured too, by [cmd/help.go](cmd/help.go), which renders cobra's usage template itself (`usageText`) so that the text can be coloured for the stream it is going to, which cobra's templates can't be told: `--help` goes to stdout, and usage after an error to stderr (rendered to a buffer by `UsageString`, so `destination` takes it for stderr), and each follows its own stream; the `Error:` prefix is `errPrefix()`, rewritten by `applyColor`. `TestUsageAndHelpAreWhatCobraWrites` checks that the plain text is what cobra's own is for every command (it caught usage losing `[flags]` for a command that only inherits flags), so a change in cobra's templates that isn't followed fails it; cobra's own Go implementation of usage misspells one heading (`topcis`), which the test accounts for. Cobra doesn't run `initConfig` to print help, a flag error or an unknown command, so `Execute` loads the config file and applies `PACKWIZ_COLOR` and the config's `color` first (`applyColorIfSet`).
- [cmdshared/](cmdshared) holds helpers shared across command packages (download progress/utilities, interactive prompts, Minecraft version lookups) that don't belong in `core`.

Because `core` doesn't import `cmd`, and source packages (`modrinth`) import both, new mod sources plug in the same way `modrinth` does: implement `core.Updater`/`core.MetaDownloader`, register in `init()`, and add a `cmd.Add()`-registered subcommand — without modifying `core` or `cmd`.

Configuration flows through `viper` globally (not passed explicitly through call chains): persistent flags are bound with `viper.BindPFlag` in `cmd/root.go`, and `Pack.Options` from `pack.toml` are merged into the same global viper config in `core.LoadPack` — so pack-level TOML options and CLI flags/env vars (`PACKWIZ_`-prefixed) are read through the same `viper.Get*` calls throughout the codebase.

## Testing conventions

Commands hold their logic directly in cobra `Run` closures that print via `fmt.Println` and exit via `os.Exit(1)` on error, rather than returning errors — so tests call `Run(cmd, args)` directly against an isolated temp directory and capture real stdout, instead of driving `rootCmd.Execute()`. [internal/cmdtest/cmdtest.go](internal/cmdtest/cmdtest.go) provides the shared helpers for this (`Chdir`, `CaptureStdout`, `SetStdin` to answer prompts, `WritePackFile`, `SetViper`/`SetViperBool`) and documents the viper state-leakage pitfalls between tests (see its doc comments, especially around `WritePackFile` and `Pack.Options` merging).

Captured stdout is a pipe, so it is plain text unless a test asks for colour: `cmdtest.SetColor(t, ui.Always)` turns it on for one test (restored on cleanup). `cmdtest.AssertColourOnlyAdds(t, fn)` runs a command's output twice, without colour and with it, and checks that the coloured output has colour and that `ui.Strip` of it is the plain output; use it for every command you colour, then check the pieces you care about with `ui.Bold.Sprint(...)`-style expectations rather than hand-written escape sequences. `cmdtest.WithoutProgress` drops the index refresh's progress bar (`Refreshing index...`, redrawn in place with cursor codes and showing elapsed time) from output that is compared exactly; tests that only use `strings.Contains` needn't. The `ui` package's tests include real pseudo-terminal ones (Linux only, skipped where `/dev/ptmx` isn't available), and `cmdtest.OpenTerminal` gives other packages one, to check that a stream that is a terminal is coloured and one that isn't is not (put in one of `os.Stdout` or `os.Stderr` at a time, with `CaptureStdout` or `CaptureStderr` for the other). A command that ends in `os.Exit(1)` can't be tested in the process; run the test binary again as a process (see `TestUpdateOneFileFailsWhenItsCheckFails`) and check its exit status and output.

The `changelog` and `git` packages are the exception: their `Run` closures are thin wrappers that print and `os.Exit(1)` on an error returned by `runPreview`/`RunRelease`/`runCommit`/`runRelease`, and tests call those functions directly, so a failure reports through `t.Fatalf` instead of killing the test binary with its captured output. The `changelog` tests read the log from a `fakeRepo` ([changelog/repository_test.go](changelog/repository_test.go)) that the test writes, so they need no git binary; the pipeline against real git (committing each mod, then releasing from the log) is tested in the `git` package.

HTTP-calling code (Modrinth API client, downloads) is tested with `github.com/jarcoal/httpmock` rather than live network calls. Tests of the version lookup in `changelog` and `git` register a stub source with `cmdtest.RegisterVersionSource`; `core`'s own tests can't import `cmdtest` (import cycle), so they define their own. The `git` package's tests run the real `git` binary in throwaway repositories isolated from the user's git config, and skip when it isn't installed (as in the Nix sandbox).

The `tui` tests drive a screen by sending it key messages and running the commands that come back (`press` and `feed` in [tui/helpers_test.go](tui/helpers_test.go)), on a real pack in a temp directory (`setUpPack`) through `packBackend`, and compare the drawn text (colour off, see `setUpPack`) and what was written to disk. `assertIndexIsConsistent` checks that a refresh would leave `index.toml` and `pack.toml` byte for byte as they are, which is how a test knows that nothing a change touched was left out of the index. `fakeBackend` is for what a screen does with errors and with data that is hard to make on disk. `TestProgramRelatesAFileFromKeyPresses` runs a real `tea.Program` with raw key bytes through a pipe; its output can't be searched as text, as the renderer draws cell by cell, so it goes by what was written to the pack, and waits (with `tea.WithFilter`) for the `loadedMsg` that follows a change before it quits, as quitting sooner would leave the write racing the test. Most screens are tested with a fake backend where the network or an error is the point, and with `packBackend` on a real pack where what is written to disk is (each of those that can also runs under `cmdtest.CaptureStdout` and expects nothing written to the terminal); `httpmock` is turned on (`httpmock.Activate(t)`) in any test that could reach Modrinth, so an unexpected request fails rather than going out. `stubUpdater` and `useUpdater` stand in for a source of updates, `addableFixture` and `exportFixture` for a Modrinth that serves a project or a file, and `setUpGit` (which skips when git isn't installed) is for the release screen, which is run against a real repository once. `feed` and `appFeed` run batches and long chains of jobs as a program does. The real thing is checked in a terminal with tmux: `tmux new-session -d -x 100 -y 28 'packwiz tui'`, then `send-keys` and `capture-pane -p` (which shows a literal tab where the renderer skipped blank cells).

## Git workflow

Prefer a fast-forward when merging a branch into `main` (`git merge --ff-only <branch>`), and only make a merge commit if a fast-forward isn't possible.
