# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is `github.com/evictedcucumber/packwiz`, a fork of [packwiz/packwiz](https://github.com/packwiz/packwiz), a CLI tool for creating Minecraft modpacks as version-controllable TOML metadata rather than raw JAR files. This fork only supports Modrinth as a mod source — CurseForge, GitHub releases, and direct-URL/local downloads have been removed from upstream. Packs created by this fork use a distinct `pack-format` (`evictedcucumber-packwiz:1.0.0`, see [core/pack.go](core/pack.go)) and are intentionally incompatible with upstream packwiz tooling.

## Commands

### Build

```bash
go build ./...
```

After any change, verify the project builds both ways CI and users build it:

```bash
go build ./...
nix build
```

`nix build` uses vendored dependencies pinned by `nix/vendor-hash`. If `go.mod`/`go.sum` changed, that hash must be refreshed: clear `nix/vendor-hash`, run `nix build`, and copy the `got:` hash from the failed build back into the file.

`nix build` only sees files git tracks, so a new, untracked file or package makes it fail (or silently build without it). Stage new files first (`git add -N` is enough), or build from a throwaway `git init` copy of the tree to leave the real index alone. `nix build` also runs `go test ./...` in a sandbox with no `git` binary.

If `go` isn't on `PATH` (this repo doesn't assume a global Go install), run it through the flake dev shell instead: `nix develop --command go build ./...`.

### Test

```bash
go test ./...
```

Run a single package or test (mirrors what CI runs, `-race -count=2`, for a specific package):

```bash
go test ./core/... -race -count=2
go test ./modrinth/... -run TestSomeName -v
```

### Vet

```bash
go vet ./...
```

### Nix dev shell

```bash
nix develop
```

Provides the Go toolchain plus `gopls`, matching `flake.nix`. `direnv` (`.envrc` has `use flake`) picks this up automatically.

## Architecture

Commands are registered into a shared root via a plugin-style `init()` pattern, not a single monolithic command tree:

- [cmd/root.go](cmd/root.go) defines the root cobra command and global persistent flags (`--pack-file`, `--meta-folder`, `--meta-folder-base`, `--cache`, `--config`, `-y/--yes`), and exposes `cmd.Add()` for other packages to register subcommands.
- [cmd/](cmd) holds source-agnostic commands: `init`, `list`, `pin`/`unpin`, `refresh`, `remove`, `rehash`, `update`, `serve`, `mark-dependency`/`unmark-dependency`. `update --all` counts the checks that failed and says "No updates found, but N files could not be checked" rather than "All files are up to date!" (its exit status is still 0 when some checks fail, as the TODOs there ask about); `update <name>` exits 1 when its check fails, as everything else that goes wrong in it does.
- [modrinth/](modrinth) implements the Modrinth source as a self-contained package: it registers its own `modrinth`/`mr` command (with `add [URL]`, `export`, `deps` subcommands) via `init()`, and implements `core.Updater` (registered into `core.Updaters["modrinth"]`) so the source-agnostic `packwiz update` can dispatch to it. [modrinth/api/](modrinth/api) is a thin REST client for the Modrinth API; the rest of [modrinth/](modrinth) contains install/export/dependency-resolution logic. `add` on a project the pack already has (found by its Modrinth project ID, since a metadata file can have any name) compares versions and, if they differ, asks before updating that mod in place rather than overwriting it: `applyVersion` in [modrinth/updater.go](modrinth/updater.go) is shared with `DoUpdate`, so the mod keeps its pin, option and so on, and a pinned mod is refused even with `-y`. Its latest version is looked up with the release type the mod was added with, so `add` and `packwiz update` agree on what is latest. `getLatestVersion` in [modrinth/modrinth.go](modrinth/modrinth.go) picks the newest by date, and warns when another version has a higher version number (`findHigherNumbered`). Only versions at least as stable are compared (so a beta running ahead of a release isn't a warning), and only those whose numbers are written the same way (`versionNumberShape`), because FlexVer gives nonsense for numbers in different formats: text sorts above a number, so it ranks `mc1.21.1-6.0.9` above `6.0.10+mc1.21.1`. A project that changed how it numbers its versions is therefore left unflagged rather than wrongly flagged. The loader tags authors put in their numbers are left out first (`comparableVersionNumber`), so versions that differ only by such a tag, like `neoforge_1.21-2.0.8` and `1.21-2.1.10`, still compare with each other. A NeoForge pack that has Sinytra Connector and Forgified Fabric API added (`runsFabricMods` in [modrinth/connector.go](modrinth/connector.go), which goes by their Modrinth project IDs) also accepts mods that only have a Fabric version: `getLatestVersion` looks for Fabric only when there is nothing for the pack's loader, so a NeoForge version always wins however old, and only a `noVersionsError` triggers it, so a failed lookup isn't taken for finding nothing. `add` says in a notice that such a mod runs through Connector, but `update` doesn't, as it would repeat it for every Fabric mod each time. Fabric API itself is never added: Forgified Fabric API stands in for it and the two can't be installed together, so it counts as already added when dependencies are resolved and in `deps`, and adding it directly is refused. `CheckUpdate` reads the index itself to know what the pack has, as the mods it is given can be just the one being updated.
- [settings/](settings) (`acceptable-versions`, `release-type`), [migrate/](migrate) (`minecraft [version]`, `loader [version|latest|recommended]`), and [utils/](utils) (`markdown`) are similarly self-registering command packages, imported for side effects only (blank imports) from [main.go](main.go).
- [changelog/](changelog) manages a pack's release history (`packwiz changelog`, `packwiz changelog release`), and makes it from the git log. `RunRelease` first has the repository commit everything pending (`Repository.CommitPending`, which is `packwiz git commit`), then reads the commits made since the last release's recorded `Release.Commit` (`Repository.Log`; `--since` overrides it, and a history from before commits were recorded falls back to the last commit that changed `changelog.toml`), and `ChangesFromCommits` ([changelog/commits.go](changelog/commits.go)) reads them as conventional commits. What `packwiz git commit` writes is read back exactly (the regexes in `commits.go` and `line()` in [git/message.go](git/message.go) are the two ends of that format, kept in step by a round-trip test in the git package), several commits to one mod or file are squashed to their net effect, and any other `feat`/`fix`/breaking commit becomes a `Note` that counts towards the bump in its own words. The versioning policy lives in `Change.Bump()` in [changelog/diff.go](changelog/diff.go): any change to a server or both-side mod is major, adding/removing a client-only mod is minor, client-only mod updates and config changes are patch, and a note is bumped by its own type. The first release has no log to read, so it describes the pack as it is (a `Snapshot` diffed against nothing). `git` imports `changelog`, so `changelog` can't import it back: it defines `Repository` and `OpenRepository`, and [git/changelog.go](git/changelog.go) implements and registers it in `init()`, the same way `core.Updaters` is filled. `CHANGELOG.md` is rendered from `changelog.toml` (`RenderRelease`, plain), and the preview that `packwiz changelog` prints goes through the same code with `style{colour: true}` (`renderRelease`), which colours pieces as they are built rather than reading Markdown back, so the text can't differ between the file and the terminal. `CHANGELOG.md` and `changelog.toml` are in `ignoreDefaults` in [core/index.go](core/index.go) so they aren't shipped inside the pack. A mod's version is what it records (`core.Mod.Version`, written by `add`/`update`); for mods that predate the field, `changelog.LoadWorking` asks their updater (`core.VersionResolver`, implemented by the Modrinth updater) and keeps the answer in memory, and only the writing path (`packwiz git commit`, which `RunRelease` runs) saves it with `Index.RecordVersions`, so previewing never touches the pack. A snapshot records a mod's file name when its version is unknown, so `modUpdated` in [changelog/diff.go](changelog/diff.go) treats a version that has merely become known for the same file as no change (which would otherwise make a server mod's commit look like a major update), and `History.UpgradeVersions` replaces file names in past releases where the mod is still on that file.
- [git/](git) implements `packwiz git commit` and `packwiz git release` by shelling out to the `git` binary (no Go git dependency). It describes changes by diffing `changelog.TakeSnapshotFrom` a `HEAD` read straight out of git (`core.ParseIndex`/`core.ParsePack`/`core.DecodeMod` parse the committed bytes) against the working tree, so it reuses `changelog.Diff` and the bump policy rather than classifying anything itself. It also supplies the log to the changelog: `gitRepository` in [git/changelog.go](git/changelog.go) implements `changelog.Repository` (`git log --reverse --no-merges` for `Log`, and `pendingCommits` from the same plan `commit --dry-run` prints). `commit` makes one commit per added/updated/removed mod, then one for everything else ([git/commit.go](git/commit.go)); each commit is a consistent pack, so before each one `committer.writeIndexAndPack` writes an index (`HEAD`'s with only the mods committed so far applied) and a `pack.toml` (`HEAD`'s with just that index's hash), and the working tree is put back to the final index and `pack.toml` afterwards, including when a commit fails. The commit-type-to-bump mapping (`feat!`/`feat`/`fix`) is documented in [git/message.go](git/message.go).
- [core/](core) has no dependency on `cmd` and holds the domain model shared by everything above: `Pack` ([core/pack.go](core/pack.go), the `pack.toml`), `Index`/`IndexFiles` ([core/index.go](core/index.go), [core/indexfiles.go](core/indexfiles.go), the `index.toml` manifest of tracked files), and `Mod` ([core/mod.go](core/mod.go), one TOML file per installed mod). [core/interfaces.go](core/interfaces.go) defines the `Updater` and `MetaDownloader` extension points that source packages implement, plus the optional `VersionResolver` an `Updater` can also implement.
- [internal/ui/](internal/ui) colours command output, and is a leaf package (it imports nothing of packwiz's) so every package can use it. Styles are named for their role, not their colour, so how they look is decided in one place: `ui.Error`, `ui.Warning`, `ui.Success`, `ui.Info`, `ui.Muted` and `ui.Bold`, each with `Sprint`/`Sprintf`/`Printf`/`Println` that work like `fmt`'s (`Printf`/`Println` write to stdout, where every command prints). **Colour only ever adds to text**: with it off each returns its text unchanged, and with it on `ui.Strip` gives that same text back. So a message is worded the same either way, and new output should be written by putting the whole line in the style of what it says (`ui.Error.Println(err)`, `ui.Success.Printf(...)`) with `ui.Bold.Sprint(name)`-style emphasis inside, never by adding a prefix or symbol. Styles nest (a style inside another ends with a reset, which the outer one starts again after) and each line is styled on its own, ending before its line break. Only style at the point of printing: never put a styled string in an `error`, a file, a git commit message or `CHANGELOG.md`. Whether to colour is decided each time, for the stream the text is going to: `os.Stdout` (`term.IsTerminal`, so a test that captures stdout through a pipe gets plain text with no setup) unless the style is `.For(f)` another file, such as `ui.Error.For(os.Stderr)`, which `Printf`/`Println` then write to. Each stream is a terminal or not on its own (`ui.EnabledFor(f)`). It is decided by `--color=auto|always|never` (`--colour` too; also `PACKWIZ_COLOR` or `color` in the config file, applied by `applyColor` in [cmd/root.go](cmd/root.go)): `always` wins over everything, and `auto` is off for `NO_COLOR` and `TERM=dumb`. Windows consoles need virtual terminal processing turned on first, and the terminals of Cygwin, MSYS2 and Git Bash (mintty) aren't consoles but pipes to a pseudo-terminal, told apart only by the name of the pipe: `isCygwinPipeName` ([internal/ui/cygwin.go](internal/ui/cygwin.go)) is tested everywhere, but the calls that read a name and turn on the console are in [internal/ui/terminal_windows.go](internal/ui/terminal_windows.go), which has only been compiled (`GOOS=windows go vet ./...`), not run. `ui.Prompt` styles a prompt from its shape (the question in bold, `[default]` in cyan, `(choices)` faded), which is why `cmdshared.PromptYesNo` and `initReadValue` style their prompts themselves and callers pass them plain. `ui.Transition(from, to)` shows an update as red old, green new. Help and usage are coloured too, by [cmd/help.go](cmd/help.go), which renders cobra's usage template itself (`usageText`) so that the text can be coloured for the stream it is going to, which cobra's templates can't be told: `--help` goes to stdout, and usage after an error to stderr (rendered to a buffer by `UsageString`, so `destination` takes it for stderr), and each follows its own stream; the `Error:` prefix is `errPrefix()`, rewritten by `applyColor`. `TestUsageAndHelpAreWhatCobraWrites` checks that the plain text is what cobra's own is for every command (it caught usage losing `[flags]` for a command that only inherits flags), so a change in cobra's templates that isn't followed fails it; cobra's own Go implementation of usage misspells one heading (`topcis`), which the test accounts for. Cobra doesn't run `initConfig` to print help, a flag error or an unknown command, so `Execute` loads the config file and applies `PACKWIZ_COLOR` and the config's `color` first (`applyColorIfSet`), and the help and flag-error hooks apply the flag (`applyColorAfterFlags`, which also loads a config file named by `--config`); pflag stops at the first flag it can't parse, so `--color` after one isn't seen.
- [cmdshared/](cmdshared) holds helpers shared across command packages (download progress/utilities, interactive prompts, Minecraft version lookups) that don't belong in `core`.

Because `core` doesn't import `cmd`, and source packages (`modrinth`) import both, new mod sources plug in the same way `modrinth` does: implement `core.Updater`/`core.MetaDownloader`, register in `init()`, and add a `cmd.Add()`-registered subcommand — without modifying `core` or `cmd`.

Configuration flows through `viper` globally (not passed explicitly through call chains): persistent flags are bound with `viper.BindPFlag` in `cmd/root.go`, and `Pack.Options` from `pack.toml` are merged into the same global viper config in `core.LoadPack` — so pack-level TOML options and CLI flags/env vars (`PACKWIZ_`-prefixed) are read through the same `viper.Get*` calls throughout the codebase.

## Testing conventions

Commands hold their logic directly in cobra `Run` closures that print via `fmt.Println` and exit via `os.Exit(1)` on error, rather than returning errors — so tests call `Run(cmd, args)` directly against an isolated temp directory and capture real stdout, instead of driving `rootCmd.Execute()`. [internal/cmdtest/cmdtest.go](internal/cmdtest/cmdtest.go) provides the shared helpers for this (`Chdir`, `CaptureStdout`, `SetStdin` to answer prompts, `WritePackFile`, `SetViper`/`SetViperBool`) and documents the viper state-leakage pitfalls between tests (see its doc comments, especially around `WritePackFile` and `Pack.Options` merging).

Captured stdout is a pipe, so it is plain text unless a test asks for colour: `cmdtest.SetColor(t, ui.Always)` turns it on for one test (restored on cleanup). `cmdtest.AssertColourOnlyAdds(t, fn)` runs a command's output twice, without colour and with it, and checks that the coloured output has colour and that `ui.Strip` of it is the plain output; use it for every command you colour, then check the pieces you care about with `ui.Bold.Sprint(...)`-style expectations rather than hand-written escape sequences. `cmdtest.WithoutProgress` drops the index refresh's progress bar (`Refreshing index...`, redrawn in place with cursor codes and showing elapsed time) from output that is compared exactly; tests that only use `strings.Contains` needn't. The `ui` package's tests include real pseudo-terminal ones (Linux only, skipped where `/dev/ptmx` isn't available), and `cmdtest.OpenTerminal` gives other packages one, to check that a stream that is a terminal is coloured and one that isn't is not (put in one of `os.Stdout` or `os.Stderr` at a time, with `CaptureStdout` or `CaptureStderr` for the other). A command that ends in `os.Exit(1)` can't be tested in the process; run the test binary again as a process (see `TestUpdateOneFileFailsWhenItsCheckFails`) and check its exit status and output.

The `changelog` and `git` packages are the exception: their `Run` closures are thin wrappers that print and `os.Exit(1)` on an error returned by `runPreview`/`RunRelease`/`runCommit`/`runRelease`, and tests call those functions directly, so a failure reports through `t.Fatalf` instead of killing the test binary with its captured output. The `changelog` tests read the log from a `fakeRepo` ([changelog/repository_test.go](changelog/repository_test.go)) that the test writes, so they need no git binary; the pipeline against real git (committing each mod, then releasing from the log) is tested in the `git` package.

HTTP-calling code (Modrinth API client, downloads) is tested with `github.com/jarcoal/httpmock` rather than live network calls. Tests of the version lookup in `changelog` and `git` register a stub source with `cmdtest.RegisterVersionSource`; `core`'s own tests can't import `cmdtest` (import cycle), so they define their own. The `git` package's tests run the real `git` binary in throwaway repositories isolated from the user's git config, and skip when it isn't installed (as in the Nix sandbox).

## Git workflow

Prefer a fast-forward when merging a branch into `main` (`git merge --ff-only <branch>`), and only make a merge commit if a fast-forward isn't possible.
